# 官方源码调查与汉化技术方案

## 1. 调查目标

本项目要翻译的是 **EEZ Studio 软件自身的操作界面**，不是用户在 EEZ Studio 中制作的 GUI 项目文本。目标覆盖所有面向使用者的可见文字，包括菜单、工具栏、面板、控件、属性、事件、数据绑定、设置、对话框、通知、错误信息、进度提示、帮助内容以及安装和首次启动界面。

## 2. 上游基准

- 上游仓库：https://github.com/eez-open/studio
- 本轮检查分支：`master`
- 本轮检查的 `package.json` 版本：`0.30.0`
- 许可证字段：`GPL-3.0-only`

注意：上游分支会持续变化。真正开始移植和构建时，必须固定到具体 commit，并在版本记录中保存 commit SHA，不能只记录分支名称。

## 3. 技术结构初步确认

官方项目使用 Electron、React、TypeScript，界面由多个 packages 共同组成。已确认的重点目录：

| 路径 | 初步职责 | 汉化关注点 |
|---|---|---|
| `packages/main` | Electron 主进程及窗口管理 | 原生应用菜单、文件对话框、系统消息框、窗口级提示 |
| `packages/eez-studio-ui` | 通用界面组件 | 通用按钮、对话框、表格、工具栏、输入控件、提示组件 |
| `packages/project-editor` | 项目编辑器 | 编辑器菜单、控件、属性、事件、项目设置、验证和构建提示 |
| `packages/instrument` | 仪器功能 | 仪器管理、通信、SCPI 相关界面与错误 |
| `packages/home` | 首页及项目入口 | 首页、模板、最近项目、项目创建向导 |
| `packages/notebook` | 笔记本功能 | 笔记本界面及相关提示 |

这只是第一轮模块地图，不代表已穷尽所有可见字符串。后续需要递归扫描整个仓库，并按运行场景补齐遗漏。

## 4. 已确认的关键事实

### 4.1 软件界面没有可直接启用的完整 i18n 机制

官方产品文档中的 Multilanguage / Texts / XLIFF 功能，描述的是 EEZ-GUI 和 Dashboard 等用户项目中的多语言文本资源。它不能直接用于翻译 EEZ Studio 自身的菜单、工具栏和属性面板。

官方还存在软件界面 i18n 功能请求：
https://www.envox.eu/tasklist/i18n-support/

因此，不能把用户项目的 Texts 面板或 XLIFF 导入导出误认为软件 UI 已经支持语言切换。

### 4.2 Electron 原生菜单包含硬编码英文

在 `packages/main/menu.ts` 中可以看到菜单标签直接写在 Electron 菜单定义中，例如文件、编辑、打开、保存、撤销、重做等菜单文字，以及文件不存在等消息框内容。

这类文字需要进入软件自身的翻译机制；同时必须保留 Electron 的 `role`、快捷键、菜单 ID 和 IPC 消息名称，不能把内部标识符翻译掉。

### 4.3 通用对话框具有动态文字来源

`packages/eez-studio-ui/generic-dialog.tsx` 显示通用对话框会根据字段定义生成界面。字段标题可能来自 `displayName`，也可能由 `humanize(fieldProperties.name)` 动态生成；枚举项又可能来自字符串、数字或对象的 `label`。

因此，单纯翻译 JSX 中的静态英文字符串是不够的。必须调查字段定义、枚举标签、校验器错误消息和进度回调等动态文字来源。

### 4.4 提示信息不只在 UI 组件中

错误、警告、校验结果和操作进度可能由各业务模块产生，再传入通用通知或对话框。后续扫描必须同时覆盖：
- UI 组件中的静态文案；
- 业务模块中的错误与提示；
- 验证器和构建流程的错误消息；
- 动态拼接字符串及插值参数；
- Electron 主进程的系统对话框；
- 第三方组件或系统原生控件暴露的文字。

## 5. 推荐的实现方向

当前不应立即对全仓库做英文到中文的盲目替换。推荐先建立一个统一的本地化层，再逐步接入各模块。

拟采用的原则：

1. 建立简体中文资源目录，源语言暂以英文为基准。
2. 为可翻译文本分配稳定的消息 ID，并保存上下文说明。
3. 提供统一的翻译函数和默认语言回退机制。
4. 对有参数的消息使用安全的占位符格式，避免破坏文件路径、数值和错误细节。
5. 对动态字段、枚举、验证器和第三方组件单独建立适配策略。
6. 原生 Electron 菜单与主进程对话框也必须读取同一套语言资源。
7. 先完成基础框架和少量端到端示范，再批量迁移，避免一次性改动过大而无法定位回归问题。

是否采用某个具体 i18n 库，需在检查当前依赖、打包方式和 Electron 主/渲染进程边界后决定。不要在未验证前增加大型依赖。

## 6. 翻译质量与兼容性要求

- 翻译所有用户可见文字，不只翻译菜单。
- 保留产品名、协议名、芯片型号、文件扩展名、API、函数名和代码标识符。
- 保留字符串中的占位符、转义符、快捷键和格式化参数。
- 不翻译用户输入内容、用户项目数据、生成代码、设备协议字段和第三方数据。
- 术语统一，优先使用简体中文技术社区常见表达。
- 中文界面必须检查文本溢出、控件宽度、换行、字体回退和快捷键显示。
- 缺少翻译时应有明确回退策略，不能显示空白或崩溃。
- 每个模块完成后都要运行和回归测试。
