# 项目规划与实施路线

本文档记录 EEZ Studio 简体中文版的实施步骤、技术判断和阶段性结果。项目状态发生变化时，应同步更新本文档。

## 一、总体原则

1. 以官方仓库 `eez-open/studio` 为上游基准，记录所采用的分支、提交和版本。
2. 优先寻找官方已有的本地化机制；如果软件界面没有可用的国际化入口，再评估低侵入式源码修改方案。
3. 界面文字可以翻译，程序内部标识符和用户项目数据不能随意翻译。
4. 每一阶段都要经过编译和实际运行验证，不以“翻译文件已完成”代替软件可用性。
5. 所有面向项目使用者的说明文档使用简体中文；代码、路径、API、构建配置和工具要求保留其必要的英文形式。

## 二、实施阶段

### 阶段 1：源码结构与本地化机制调查

- [ ] 确认上游版本、默认分支和构建依赖。
- [ ] 梳理主程序入口、菜单、工具栏、面板、属性编辑器、设置、弹窗和错误提示所在模块。
- [ ] 检查是否存在软件界面级国际化框架、语言资源文件或运行时语言切换入口。
- [ ] 区分软件界面文字与用户创建的 GUI 项目文本资源。
- [ ] 形成源码位置清单和本地化技术方案。

### 阶段 2：翻译体系设计

- [ ] 建立简体中文术语表。
- [ ] 设计翻译资源的组织方式和缺失翻译回退规则。
- [ ] 明确占位符、快捷键、复数、动态文本和技术名称的处理规则。
- [ ] 确保翻译不会改变程序逻辑、数据结构和项目文件兼容性。

### 阶段 3：界面汉化与验证

- [ ] 按模块实施翻译。
- [ ] 检查菜单、工具栏、控件面板、属性、事件、设置和对话框。
- [ ] 检查动态提示、错误信息、长文本、窗口缩放和中文字体显示。
- [ ] 使用代表性项目验证打开、编辑、保存、生成代码等核心流程。

### 阶段 4：自动构建与发布

- [ ] 在干净环境验证依赖安装和官方构建流程。
- [ ] 建立 GitHub Actions 自动构建。
- [ ] 优先完成 Windows 64 位安装包。
- [ ] 保存构建日志、版本信息和必要的校验信息。
- [ ] 发布时同步提供对应源码、许可证和第三方许可信息。

### 阶段 5：持续维护

- [ ] 跟踪官方版本和重要修复。
- [ ] 评估上游更新对汉化补丁的影响。
- [ ] 更新术语表和翻译资源。
- [ ] 对每个发布版本执行回归测试。

## 三、当前已知技术信息

根据已检查的官方源码：

- 项目使用 Electron、React 和 TypeScript。
- 源码采用多个 `packages` 模块组织。
- 主要相关目录包括 `packages/main`、`packages/eez-studio-ui` 和 `packages/project-editor`。
- 官方 `package.json` 提供 `build`、`pack` 和 `dist` 等构建脚本。
- 官方仓库包含 GitHub Actions 工作流，可作为研究自动构建的参考。

官方产品资料提到的多语言支持，主要针对用户设计的 GUI 项目文本资源，并提供 XLIFF 导入/导出；这不能直接证明软件自身菜单和编辑器界面已经支持切换语言。因此，必须单独调查软件 UI 的本地化机制。

## 四、当前下一步

优先检查以下模块中的可见文本来源和组件组织：

1. `packages/eez-studio-ui`
2. `packages/main`
3. `packages/project-editor`

调查结果应记录具体文件路径、文本类型、是否动态生成，以及推荐的翻译处理方式。完成调查后再决定是采用统一翻译资源、包装翻译函数，还是局部源码替换；暂不提前确定实现方式。
